# Future Live-Mode Readiness Guide

## Current status

Ledgerline is **not armable for real trading** in this branch. Binance venue mutations, Sailor mutations, and MCP activation are deliberately sealed in code. Setting a feature flag, changing a local configuration file, creating an API key, changing a mandate, or calling an internal procedure cannot lift that boundary.

> This document replaces the former step-by-step arming instructions. It is a governance and readiness reference only; it is **not** an operational runbook for connecting an exchange, adding credentials, or placing/cancelling an order.

| Capability | Current state | Enforced boundary |
|---|---|---|
| Paper simulation | Available | Owner-scoped policy and mandate checks |
| Public market and on-chain evidence | Available where permitted | Read-only adapters and response validation |
| Binance order placement or cancellation | Sealed | Service boundary rejects before key decryption or venue I/O |
| Sailor mutations | Sealed | Service boundary and owner-scoped mandate resolution |
| MCP process or HTTP activation | Sealed | Manager rejects activation and unsafe configuration |
| API-key verification | Not an activation path | New keys remain `testing`; no execution authority follows |

## What the security remediation adds

The `fix/security-binance` integration adds defence in depth around the future execution architecture. It retains authority-state and mandate validation for direct callers, but a sealed boundary prevents any externally effectful request after those checks. A single database-backed idempotency intent and a user/day risk reservation are prepared for a future programme; they are not authorization to use a venue.

Client-originated entries are limited to explicitly non-authoritative owner notes. Control events, authority transitions, and security signals must be generated by server-controlled paths. Sensitive mutations are subject to an authenticated same-origin boundary when an Origin header is supplied and per-user/path rate limiting.

## Required staging migration

The generated migration `drizzle/0010_lethal_mikhail_rasputin.sql` prepares only database structures: `liveOrderIntents`, `liveDailyRiskBuckets`, the `owner_note` action kind, and the `testing` default for platform keys. It is safe to review and test in staging under the conditions below; it **does not** unseal venue mutations.

Before an operator applies it in staging, they must verify a current backup, confirm the recorded migration head is `0009_youthful_sir_ram`, use an account with `CREATE TABLE` and `ALTER TABLE` permissions, run `pnpm drizzle-kit check` from the exact commit, and schedule the two `ALTER TABLE` statements in a maintenance window. The migration must first be trialled against a staging clone. It must never be applied automatically from a browser action or as part of a `main` merge.

## Future programme gates

Any future real-mode proposal must be a separate security programme with a new architecture decision record, threat model, approval design, and independent review. At minimum it must demonstrate hardware-backed secret isolation, a server-secret-bound approval design, reproducible database migration and rollback drills, exchange sandbox reconciliation, horizontally shared rate limits, incident response ownership, monitoring, and a staged exposure plan.

The proposal must be reviewed through the standard branch workflow: a dedicated short-lived `feature/*` branch, PR to `staging`, green CI and migration rehearsal, explicit owner approval, then a separate promotion of tested `staging` to `main`. No configuration edit, branch merge, or CLI command is a substitute for these gates.
